\subsection{Introduction to Greennode Corporation}

\subsubsection{General Information}

GreenNode is a Vietnam-based sovereign, high-performance AI cloud provider and a member of VNG Digital Business, under VNG Corporation, Vietnam's first technology unicorn, founded in 2004. In late 2025, VNG merged its cloud computing unit, VNG Cloud, with its AI infrastructure unit, GreenNode, into a single unified AI cloud brand, and this positioned it as one of the few platforms in Vietnam offering both conventional cloud and high-performance AI cloud on a unified ecosystem, letting customers train, fine-tune, and deploy AI models on the same infrastructure. As a preferred NVIDIA Cloud Service Partner in Southeast Asia, GreenNode offers enterprises high-performance NVIDIA H100 GPU infrastructure across data centers in Vietnam and Thailand, and it has supported over 1,000 domestic and international enterprises with a strong presence in markets such as the United States, MENA, and APAC, alongside active operations in Vietnam, Thailand, and Singapore. Its portfolio spans cloud infrastructure, AI/ML services, and data management and process-automation solutions, including PaaS offerings like vDB, Kafka, and VKS, as well as its in-house GreenNode IDP (Intelligent Document Processing) solution, which combines OCR, Generative AI, and LLMs to extract and validate data from complex documents.

\subsubsubsection{Week 6: Container Runtime Benchmarking}

\subsubsubsection*{Task Description}

\begin{itemize}
    \item \textbf{Container Runtime Comparison}
    \begin{itemize}
        \item Studied three container runtimes commonly used in sandboxes:
        \begin{itemize}
            \item \textbf{runsc (gVisor):} user-space kernel, strong isolation, higher overhead.
            \item \textbf{kata-fc (Firecracker):} lightweight hypervisor, balance of isolation and performance.
            \item \textbf{kata-qemu:} full QEMU hypervisor, maximum isolation, highest overhead.
        \end{itemize}
    \end{itemize}

    \item \textbf{Hypervisor-Based Isolation}
    \begin{itemize}
        \item Studied hypervisor-based runtimes, where each sandbox runs inside a lightweight virtual machine instead of sharing the host kernel directly.
        \item Compared Firecracker-based \texttt{kata-fc} and QEMU-based \texttt{kata-qemu} with OS-level containers and gVisor.
        \item Evaluated the stronger VM-level security boundary for untrusted agent code, together with the additional virtualization overhead.
        \item Analyzed the trade-off: hypervisor runtimes generally provide stronger isolation but require more memory and have higher startup latency than ordinary containers.
    \end{itemize}

    \item \textbf{Benchmark Design and Execution}
    \begin{itemize}
        \item Designed benchmark suite:
        \begin{itemize}
            \item Pod startup time.
            \item Code execution latency (simple Python scripts, system calls).
            \item Memory footprint per sandbox.
            \item Network throughput (inter-pod communication).
        \end{itemize}
        \item Implemented benchmarks using Python and Kubernetes.
        \item Ran each runtime 10+ times to reduce noise; collected timing and resource data.
        \item Analyzed overhead: CPU cycles, memory, and I/O costs compared to native execution.
    \end{itemize}

    \item \textbf{Trade-off Analysis}
    \begin{itemize}
        \item Created comparison tables and graphs (isolation strength vs. performance overhead).
        \item Assessed which runtime is best for different use cases (e.g., low-latency agent tools vs. untrusted code).
    \end{itemize}
\end{itemize}

\subsubsubsection*{Results / Knowledge Gained}

\begin{itemize}
    \item Obtained quantitative benchmark data on container runtime performance.
    \item Understood isolation vs. performance trade-offs in practical terms.
    \item Developed data-driven insights for runtime selection.
    \item Created benchmark methodology suitable for ongoing performance monitoring.
\end{itemize}

    \item \textbf{Architectural Evolution Plan: LangGraph to Deep Agent Harness Migration}
    \begin{itemize}
        \item \textbf{Strategic Assessment:}
        \begin{itemize}
            \item Evaluated LangGraph as a low-level engine: good for prototyping, but lacks built-in harness features for production deployment.

            \item Determined that transitioning to deep agent harness engine provides higher-level abstractions for enterprise use.
        \end{itemize}

        \item \textbf{Migration Strategy:}
        \begin{itemize}
            \item \textbf{Phase 1 - Foundation:} Replace LangGraph state management with harness-native context and observation layers.
            \item \textbf{Phase 2 - Governance:} Migrate to harness governance model (approval mechanisms, cost tracking, audit logging).
            \item \textbf{Phase 3 - Orchestration:} Adopt harness-native multi-agent coordination and swarm patterns.
            \item \textbf{Phase 4 - Optimization:} Leverage harness-native memory, tool calling, and distributed tracing.
        \end{itemize}

        \item \textbf{Benefits of Harness Engine:}
        \begin{itemize}
            \item \textbf{Stability:} Enterprise-grade error handling, resilience patterns, and production safeguards.
            \item \textbf{Scalability:} Native support for distributed deployment, horizontal scaling, and resource management.
            \item \textbf{Observability:} Built-in instrumentation, monitoring, and governance audit trails.
            \item \textbf{Developer Experience:} Higher-level abstractions reduce complexity, accelerate feature development, improve code maintainability.
        \end{itemize}
